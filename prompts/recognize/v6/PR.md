# Как работает промпт (простыми словами)

Промпт — это инструкция для AI-модели, которая превращает «сырой» ввод (подписи к фото, текст сообщения) в аккуратный JSON-список продуктов. У него **два режима работы**, и `accumulate` — это второй.

---

## 1. Режим `single` (одиночный, по умолчанию)

**Когда:** пользователь прислал один вход и всё.

**Что делает модель:** берёт этот вход → отдаёт один JSON-список продуктов.

**Пример:**
> Вход: «молоко 1л, сыр, яйца 10 шт»
>
> Выход:
> ```json
> {"products":[
>   {"name":"молоко","quantity":1,"unit":"л"},
>   {"name":"сыр","quantity":null,"unit":null},
>   {"name":"яйца","quantity":10,"unit":"шт"}
> ],"mode":"single"}
> ```

Никакой памяти между запросами нет — каждый раз «с чистого листа».

---

## 2. Режим `accumulate` (накопительный)

**Когда включается:** пользователь присылает **несколько сообщений/фото подряд** и хочет, чтобы они складывались в **единый список за всю сессию**. Признаки во входе: «ещё», «добавь», «дополнительно», «второе фото», «итого», либо явно передан `previous_products`.

**Что делает модель:**
1. Берёт **предыдущий список** (`previous_products`).
2. Разбирает **новый вход**.
3. **Сливает** их по правилам:
   - одинаковое название → **суммирует количество** (если единицы совместимы: кг↔г, л↔мл переводятся);
   - новое название → **добавляет в конец**;
   - конфликт единиц (шт vs кг) → **не складывает**, оставляет две записи, снижает `confidence` до 0.6.
4. Возвращает **объединённый список** + поле `duplicates_merged` (сколько дублей склеено).

**Пример (из промпта, Пример 7):**
> Предыдущий список: `[{"name":"молоко","quantity":1,"unit":"л"}]`
> Новый вход: «ещё фото: молоко 0.5 л, хлеб»
>
> Выход:
> ```json
> {"products":[
>   {"name":"молоко","quantity":1.5,"unit":"л","source":"merged"},
>   {"name":"хлеб","quantity":null,"unit":null,"source":"photo"}
> ],"mode":"accumulate","duplicates_merged":1}
> ```
> Молоко **склеилось** (1 + 0.5 = 1.5 л), хлеб **добавился**.

---

## 3. Что с этим делать разработчику (практика)

### Вариант А — «тупой» stateless-подход (проще всего)
Каждый запрос — отдельный вызов модели в режиме `single`. Если нужно накопление — **сам разработчик** хранит список на бэкенде (в БД/сессии) и при следующем запросе передаёт его в `previous_products`. Модель просто сливает.

```
[Клиент] → фото 1 → [Бэкенд] → модель (single) → список A
[Клиент] → фото 2 → [Бэкенд] берёт A, кладёт в previous_products → модель (accumulate) → список A+B
```

### Вариант Б — «умный» подход
Модель сама определяет режим по тексту («ещё», «добавь» и т.п.). Но тогда **нужно хранить контекст диалога** (историю сообщений) — иначе модель не знает, что было раньше. Это дороже по токенам.

**Рекомендация:** для продакшена — **Вариант А**. Явно передавать `previous_products` надёжнее, чем полагаться на распознавание слов-триггеров.

---

## 4. Ключевые поля JSON, которые надо обработать на бэкенде

| Поле | Зачем |
|---|---|
| `products[]` | сам список (name, quantity, unit) |
| `confidence` | 0.0–1.0, насколько модель уверена (низкое → можно показать пользователю «проверьте») |
| `mode` | `single` или `accumulate` — чтобы понять, сливать или нет |
| `duplicates_merged` | сколько дублей склеено (для логов/аналитики) |
| `source` | откуда продукт: `photo` / `text` / `merged` |
| `added_at` | номер шага, на котором появился |

---

## 5. Важные нюансы, о которые легко споткнуться

1. **Формат ответа строгий:** первый символ — `{`, никакого markdown. Если модель обернёт в ```` ```json ```` — парсер сломается. Стоит добавить пост-обработку (strip code fences) на всякий случай.
2. **Ошибки — это тоже текст, не JSON.** При отказе модель вернёт фразу «Ошибка: Входные данные не являются списком продуктов…». Бэкенд должен это распознавать (не пытаться парсить как JSON).
3. **В `accumulate` при ошибке шага список НЕ меняется** — возвращается «Ошибка шага: …». То есть старый список надо сохранить как есть.
4. **Единицы нормализованы** только к `шт / кг / г / л / мл`. «Пачка», «бутылка», «батон» → `шт`.
5. **Десятичный разделитель — точка** (`1.5`, не `1,5`).
6. **Термическая обработка** (варка/жарка) — это правило для следующего этапа (генерация рецептов), а не для парсинга продуктов. На выходе парсера его нет, оно применяется позже.

---

## 6. Что делать с `accumulate`?
>
> 1. Храни текущий список продуктов в сессии/БД.
> 2. При новом вводе передавай его в `previous_products`.
> 3. Вызывай модель, получай объединённый JSON.
> 4. Заменяй сохранённый список новым.
> 5. Если пришла «Ошибка шага…» — список **не трогай**.
>
> Всё. `accumulate` — это просто «режим слияния», модель склеивает старый и новый списки по правилам (сумма количеств при совпадении названий, добавление новых, конфликт единиц → две записи).
