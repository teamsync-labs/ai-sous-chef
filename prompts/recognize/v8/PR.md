# Как будет обрабатываться промпт при добавлении продуктов пользователем

Короткий ответ: **промпт этого не описывает — и это пробел.** Текущая версия рассчитана на один «снимок» входа (список или подписи с фото) и не содержит правил для сценария «пользователь хочет дополнить уже сформированный список». Ниже — разбор того, что произойдёт на практике, и как это исправить.

---

## 1. Что произойдёт с текущим промптом

### Вариант А: пользователь дописывает продукты в тот же вход
Например, было «молоко 1 л, сыр», пользователь добавляет «и ещё хлеб, яйца 10 шт».
Промпт обработает **весь вход заново** как единый список: правило «Удаляй дубликаты» и «Не добавляй продукты, которых нет во входе» сработают корректно, на выходе будет полный список. **Проблема:** если пользователь дописывает только новинки («добавь хлеб»), модель может:
- либо вернуть только «хлеб» (восприняв вход как новый список) — и потерять прежние позиции;
- либо попытаться объединить с предыдущим ответом — но промпт **не даёт доступа к предыдущему ответу** и не содержит инструкции «объедини с прошлым списком».

Итог: поведение непредсказуемо, зависит от того, передал ли оркестратор историю диалога.

### Вариант Б: пользователь присылает новое фото/список
Промпт обработает его как **новый независимый вход**. Прежний список не сохраняется, объединения не происходит. Если оркестратор не склеивает ответы, пользователь получит два разрозненных JSON.

### Вариант В: пользователь говорит «добавь ещё 2 кг муки к уже имеющемуся»
Промпт не умеет **суммировать количества** (нет правила «сложи quantity для одинаковых продуктов»). Он либо создаст дубликат, либо (по правилу «удали дубликаты») оставит одну запись — но какое количество, не определено. Скорее всего, модель оставит последнее упомянутое или первое — непредсказуемо.

### Вариант Г: пользователь просит «убери сыр» / «замени молоко на кефир»
Промпт **не поддерживает редактирование и удаление**. Такие фразы не являются списком продуктов и могут:
- попасть под критерий отказа №4 («неполное предложение без существительных-продуктов») — хотя «сыр» и «молоко» там есть, так что отказ не сработает;
- быть восприняты как новый вход, где «сыр» — продукт, а «убери» — стоп-слово. Тогда модель вернёт `{"products": [{"name": "сыр", ...}]}`, что противоположно намерению пользователя.

---

## 2. Корневые причины

1. **Промпт stateless.** Он не знает о предыдущих ответах и не содержит правил слияния.
2. **Нет режима «дополнение».** Все инструкции написаны для полного входа, а не для дельты.
3. **Нет правил арифметики количеств** (сложение, замена, удаление).
4. **Критерии отказа не покрывают команды редактирования** («убери», «замени», «добавь» — это не мусор и не вопрос, но и не список продуктов).
5. **Нет указания, что делать с историей диалога** — передаётся ли она модели, в каком виде, считается ли предыдущий JSON авторитетным.

---

## 3. Как это исправить — три подхода

### Подход 1: «Полный вход каждый раз» (простейший)
Оркестратор сам склеивает прежний список с новыми словами пользователя и передаёт промпту **полный** вход. Промпт не меняется, но нужно добавить в него явное правило:

> **РЕЖИМ ВХОДА.** Вход всегда содержит полный актуальный список продуктов. Если пользователь дописывает продукты — считай, что они уже включены во вход. Не пытайся объединять с предыдущими ответами: предыдущего ответа не существует.

Плюс: минимум изменений. Минус: ответственность за склейку — на оркестраторе, а не на модели.

### Подход 2: «Дельта + состояние» (надёжнее)
Промпт получает два блока: `current_products` (предыдущий JSON) и `user_update` (что добавил пользователь). Нужно добавить раздел:

> **РЕЖИМ ДОПОЛНЕНИЯ.** Если во входе есть блок `current_products` и блок `user_update`:
> - обработай `user_update` по общим правилам;
> - объедини с `current_products`:
>   - одинаковые продукты (после нормализации) — **сложи quantity**, если единицы совпадают;
>   - если единицы разные (кг vs шт) — оставь две записи с разными unit и понизь confidence до 0.5;
>   - если у одной записи quantity: null, а у другой число — возьми число;
> - удали дубликаты;
> - верни полный объединённый список.
>
> Если блоков нет — работай как с обычным входом.

Плюс: явная семантика, модель не гадает. Минус: нужно менять схему входа (оркестратор должен передавать `current_products`).

### Подход 3: «Команды редактирования» (максимально дружелюбно)
Добавить распознавание команд поверх списка:

> **КОМАНДЫ РЕДАКТИРОВАНИЯ.** Если вход содержит команду «добавь», «убери», «замени», «удали» — это не отказ и не новый список. Применяй команду к `current_products` (если он передан) и верни обновлённый полный список:
> - «добавь X» → добавь X по общим правилам;
> - «убери X» → удали X из списка;
> - «замени X на Y» → удали X, добавь Y с тем же quantity/unit, если они не указаны для Y;
> - если `current_products` не передан — верни ошибку: «Ошибка: нет текущего списка для редактирования. Передайте список продуктов.»
>
> Команды редактирования **не являются стоп-словами** и не ведут к отказу.

Плюс: покрывает реальные сценарии. Минус: усложняет промпт и требует от оркестратора передавать состояние.

---

## 4. Рекомендация

Для продакшена — **комбинация подходов 2 и 3**: оркестратор передаёт `current_products`, промпт умеет и складывать дельту, и применять команды редактирования. Подход 1 — как fallback, если состояние не передаётся.

Минимальный набор правок в текущий промпт:

1. Добавить раздел **«РЕЖИМ ДОПОЛНЕНИЯ И РЕДАКТИРОВАНИЯ»** (подход 2 + 3).
2. В критерии отказа добавить оговорку: команды «добавь/убери/замени» **не являются** основанием для отказа, если передан `current_products`.
3. В самопроверку добавить пункт: «Если был `current_products` — все прежние продукты сохранены (кроме удалённых командой)?»
4. В формат ответа — оставить ту же схему (полный список), чтобы оркестратор всегда получал актуальное состояние, а не дельту.

---

## 5. Пример нового фрагмента промпта

```
# РЕЖИМ ДОПОЛНЕНИЯ И РЕДАКТИРОВАНИЯ

Вход может содержать два блока:
- current_products — предыдущий список продуктов (JSON по той же схеме);
- user_update — текст от пользователя (новые продукты или команда).

Если блоки присутствуют:
1. Обработай user_update по общим правилам.
2. Примени к current_products:
   - «добавь X» → добавь X;
   - «убери X» / «удали X» → удали X;
   - «замени X на Y» → удали X, добавь Y (quantity/unit наследуй от X,
     если для Y не указаны явно);
   - новые продукты без команды → добавь.
3. Объедини одинаковые продукты после нормализации:
   - единицы совпадают → сложи quantity;
   - единицы разные → оставь две записи, confidence ≤ 0.5;
   - одна запись с quantity: null, другая с числом → возьми число.
4. Удали дубликаты.
5. Верни полный обновлённый список (не дельту).

Если current_products не передан, а user_update содержит команду
редактирования («убери», «замени», «удали») — верни ошибку:
«Ошибка: нет текущего списка для редактирования. Передайте список продуктов.»
```

Такой фрагмент закрывает сценарий «пользователь захотел добавить продукты» и не ломает существующую логику для обычного входа.
