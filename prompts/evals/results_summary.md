# Сводка результатов eval и типовые провалы

## Введение

Данный документ содержит результаты прогона eval-кейсов для промптов бота "Что приготовить?", а также детальный разбор типовых провалов, выявленных в ходе тестирования версии v1, и описание мер, принятых для их устранения в версии v2.

**Цель:** Обеспечить прозрачность процесса разработки промптов и дать команде уверенность в качестве финального решения.

## Детальное описание провалов

### Провал #1: Добавление продуктов "из воздуха"

| Поле | Содержание |
|------|------------|
| **Где проявился** | Кейс №5 (`fixtures/rice.txt`) |
| **Версия промпта** | `recipes/v1` |
| **Что пошло не так** | На входе только "рис", LLM вернула 3 рецепта, в каждом добавила морковь, лук, мясо и специи, которых не было в списке. Это нарушает пользовательский бюджет и вводит в заблуждение. |
| **Пример ошибки** | **Вход:** `"рис"`<br>**Выход:** `"Плов с курицей"` (добавлены курица, морковь, лук)<br>`"Рис с овощами"` (добавлены морковь, горошек)<br>`"Рисовая каша"` (добавлены молоко, сахар) |
| **Корень проблемы** | LLM обучена на "полноценных" рецептах и считает, что "помогает" пользователю, дополняя список базовыми продуктами. В system-промпте не было явного запрета. |
| **Как закрыли в v2** | 1. Добавлен строгий запрет в `system.md`: _«Используй ТОЛЬКО продукты из входного списка. Запрещено добавлять продукты, которых нет в списке, даже если они кажутся очевидными (соль, перец, масло — исключение, только если они явно указаны)»_.<br>2. Добавлена логика: если продуктов мало — вернуть 1 простой рецепт (например, "Рис отварной с маслом"), а не 3 с добавками. |
| **Результат** | ✅ Полностью исправлено. Теперь на "рис" приходит 1 рецепт без добавок. |
| **Diff (v1 → v2)** | **v1:** `"Составь 3 рецепта из списка продуктов"`<br>**v2:** `"Составь рецепты, используя ТОЛЬКО продукты из списка. Если продуктов мало — верни 1 рецепт. Если продуктов недостаточно для полноценного блюда — верни ошибку."` |

### Провал #2: Шаги без опоры ("до готовности")

| Поле | Содержание |
|------|------------|
| **Где проявился** | Кейс №2 (`fixtures/medium_products.txt`) |
| **Версия промпта** | `recipes/v1` |
| **Что пошло не так** | Шаг в рецепте звучал: _"Тушите до готовности"_. Пользователь не знает, сколько это: 10 минут или час. Это делает рецепт бесполезным. |
| **Пример ошибки** | **Вход:** `"курица, картофель, лук, морковь"`<br>**Выход:** `"Шаг 4: Тушите до готовности картофеля."` |
| **Корень проблемы** | LLM избегает конкретных цифр, чтобы не "ошибиться". Нет явного требования указывать время. |
| **Как закрыли в v2** | 1. Добавлен в `system.md`: _«Все шаги должны содержать конкретное время (в минутах) или визуальный ориентир (например, "до золотистой корочки", "до мягкости вилкой")»_.<br>2. Приведены примеры: _«Тушите 25–30 минут до мягкости»_ вместо _«Тушите до готовности»_. |
| **Результат** | ✅ Полностью исправлено. Все шаги теперь содержат временные ориентиры. |
| **Diff (v1 → v2)** | **v1:** `"Опиши пошаговый рецепт"`<br>**v2:** `"Опиши пошаговый рецепт. В каждом шаге укажи точное время в минутах (например, 'жарьте 5–7 минут') или конкретный визуальный ориентир ('до румяности', 'до мягкости вилкой')."` |

### Провал #3: Невалидный JSON / лишний текст вокруг JSON

| Поле | Содержание |
|------|------------|
| **Где проявился** | Кейс №10 (`fixtures/json_error.txt`) |
| **Версия промпта** | `recipes/v1` |
| **Что пошло не так** | LLM вернула ответ: _«Вот ваш рецепт! {"status": "ok", "recipes": [...]}»_. Бэкенд не смог спарсить JSON из-за лишнего текста. |
| **Пример ошибки** | **Выход:** `"Отличный выбор! Вот что можно приготовить: \n\n{"status":"ok","recipes":[...]}"` |
| **Корень проблемы** | Даже если в system-промпте написано "верни только JSON", LLM иногда добавляет "вежливые" фразы. |
| **Как закрыли в v2** | 1. В `system.md` усилена формулировка: _«Верни ТОЛЬКО JSON-объект. НИКАКОГО текста до или после JSON. Только { ... }»_.<br>2. В бэкенде добавлен **пост-процессинг**: перед парсингом вырезается всё до первой `{` и после последней `}`. |
| **Результат** | ⚠️ Частично: LLM стала реже добавлять текст, но 100% гарантию даёт только пост-процессинг на бэкенде. |
| **Diff (v1 → v2)** | **v1:** `"Верни ответ в формате JSON"`<br>**v2:** `"Верни ТОЛЬКО JSON. Никаких пояснений, приветствий, заключений. Только объект JSON, начинающийся с { и заканчивающийся }."` |

### Провал #4: Игнор параметров cuisine и diet

| Поле | Содержание |
|------|------------|
| **Где проявился** | Кейс №8 (`fixtures/asian_cuisine.txt`) и №9 (`fixtures/vegan.txt`) |
| **Версия промпта** | `recipes/v1` |
| **Что пошло не так** | Пользователь указал `cuisine: asian`, но LLM вернула европейский рецепт. Аналогично с `diet: vegan` — в рецепте было яйцо. |
| **Пример ошибки** | **Вход:** `курица, рис, соевый соус` + `cuisine: asian`<br>**Выход:** `"Курица с рисом в сливочном соусе"` (без соевого соуса) |
| **Корень проблемы** | Переменные `cuisine` и `diet` не были переданы в user-промпт. LLM просто не знала о них. |
| **Как закрыли в v2** | В `user.md.j2` добавлены условные блоки:<br>```jinja<br>{% if cuisine %}Желаемая кухня: {{ cuisine }}.{% endif %}<br>{% if diet %}Диетические ограничения: {{ diet }}.{% endif %}<br>```<br>Теперь эти параметры явно передаются в запрос. |
| **Результат** | ✅ Полностью исправлено. |
| **Diff (v1 → v2)** | **v1:** `"У меня есть продукты: {{ products }}"`<br>**v2:** `"У меня есть продукты: {{ products }}. {% if cuisine %}Желаемая кухня: {{ cuisine }}.{% endif %} {% if diet %}Диетические ограничения: {{ diet }}.{% endif %}"` |

### Провал #5: Потеря точности в нормализации (дроби)

| Поле | Содержание |
|------|------------|
| **Где проявился** | Кейс №6 (`fixtures/mixed_units.txt`) |
| **Версия промпта** | `normalize_products/v1` |
| **Что пошло не так** | Вход: `"курица 1.5 кг"`. Выход: `{ "quantity": 1, "unit": "кг" }`. Потеряли 0.5 кг — критично для точного расчёта. |
| **Пример ошибки** | **Вход:** `"курица 1.5 кг, картофель 500г"`<br>**Выход:** `[{"name":"курица","quantity":1,"unit":"кг"}, {"name":"картофель","quantity":500,"unit":"г"}]` |
| **Корень проблемы** | Регулярное выражение в промпте парсило только целые числа (int), не поддерживая float. |
| **Как закрыли в v2** | В `system.md` для normalize добавлено: _«Сохраняй дробные значения: 1.5, 0.5, 2.5 и т.д. Не округляй»_.<br>В валидатор бэкенда добавлена проверка на `float` вместо `int`. |
| **Результат** | ✅ Полностью исправлено. |
| **Diff (v1 → v2)** | **v1:** `"Извлеки количество (целое число)"`<br>**v2:** `"Извлеки количество (целое или дробное число, например, 1.5 кг)"` |

## Единственный оставшийся fail в v2

**Кейс 3 (`evil_products.txt`):** вредный текст с неопределённостями.

**Вход:** `"нужно срочно купить что-то из еды, но я хз что. может, макароны? там есть где-то творог, но не помню. а, и ещё вчера закончился хлеб. и огурцов хочется. помидоры тоже. ой, ещё курицу забыл. ну и молоко, если есть деньги. короче, как-то так."`

**Статус:** пройден при `temperature=0.2`, но при `temperature=0.5` может выдать fail.

**Рекомендация:** зафиксировать `temperature=0.2` в конфиге для всех промптов, чтобы снизить вариативность ответов.
